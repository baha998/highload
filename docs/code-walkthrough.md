# Как читать реализацию перед защитой

Этот маршрут объясняет назначение функций и ключевых конструкций. Файлы `gen/` созданы официальными генераторами: на защите важен исходный `.proto`, различие field number/type/presence и роль generated client/server, а не заучивание protobuf runtime.

## 1. Domain

`Product` — значение, описывающее сохранённый товар. JSON tags задают имена полей HTTP API, а не имена столбцов БД. Экспортированные Go-поля начинаются с большой буквы, поэтому доступны JSON encoder и другим пакетам.

`Clone` сначала получает копию структуры через value receiver, затем заменяет map и slice копиями. Изменение копии не меняет original. `time.Time`, числа и строки безопасно копируются по значению.

`CreateProduct` содержит только разрешённые клиенту поля. Отдельный тип предотвращает случайное управление ID, version и временем через POST. `Changes` содержит pointers; `nil` выражает отсутствие изменения. Встраивание Changes в UpdateProduct делает поля плоскими в JSON. Page одинаково описывает результат бизнес-логики для обоих транспортов.

`ErrorKind` — именованный тип на основе uint8, константы начинаются с 1 через iota; 0 означает неизвестную внутреннюю ошибку. `*Error` реализует interface error методом Error() string. NewError возвращает новый экземпляр. KindOf использует errors.As, чтобы находить доменную ошибку даже внутри fmt.Errorf с `%w`.

## 2. Repository

`Memory` содержит mutex и пять maps: товары, категории, бренды, уникальные SKU и отсортированный индекс категории. Поля закрыты для других пакетов. Объект используется по указателю; mutex нельзя копировать после начала использования.

`NewMemory` выделяет maps через make и заполняет seed до передачи repository другим goroutine. Поэтому при инициализации lock не нужен. Детерминированное время и названия делают payload-измерения воспроизводимыми.

`Get`: проверить отмену → RLock → defer RUnlock → проверить отмену после ожидания → lookup → Clone. Форма `value, ok := map[key]` отличает отсутствие ключа от нулевого значения.

`List`: под RLock проверить категорию, бинарным поиском найти начало после курсора, скопировать максимум limit элементов. Проверка отмены внутри цикла позволяет прервать обход. NextCursor пока содержит внутренний lastID; service заменит его внешним token. Если ещё остались элементы, последняя возвращённая ID становится границей следующей страницы.

`validateReferences` вызывается только из методов с уже взятым Lock: отдельная блокировка внутри привела бы к deadlock, поскольку RWMutex не reentrant. Проверка SKU допускает текущего владельца при обновлении.

`insertIndex`: найти позицию, увеличить длину среза, сдвинуть хвост через copy, вставить ID. Вызывается только под Lock; на старте seed ID уже добавлены в нужном порядке.

`Create`: Lock защищает весь набор действий — проверки существования ID и ссылок, уникальность SKU, обновление products/skus и индекса. Возвращаемый Product копируется, поэтому клиент не получает map/slice, сохранённые внутри.

`Update`: найти текущий Product и сравнить version **под тем же Lock, который защищает запись**. При переносе категории удалить ID из старого отсортированного среза и вставить в новый. Затем обновить индекс SKU, установить version+1, заменить Product и вернуть копию. После commit нет проверки ctx, которая превратила бы уже выполненный успех в ошибку и помешала кешировать результат POST.

## 3. Service

`Repository` объявляет только четыре нужных use case операции. `ProductService` хранит зависимость, переданную через New, а не ищет её в global singleton. `checkContext` через select неблокирующе проверяет закрытие ctx.Done.

`Get` валидирует ID и делегирует чтение. `List` устанавливает default limit, проверяет диапазон, декодирует base64url JSON, связывает курсор с категорией, вызывает repository и кодирует lastID обратно в token. Ошибки кодирования обёрнуты через `%w`, чтобы сохранять причину.

`validate` — общая политика для создания и обновления. `strings.TrimSpace` используется для проверки пустоты, но сервис не меняет SKU автоматически. Отдельные ограничения защищают RAM/CPU; они не заменяют лимит транспортного сообщения. Math.IsNaN/IsInf нужны в том числе из-за double в protobuf.

`Create` переводит input в Product, проверяет бизнес-поля, читает 16 случайных байт, устанавливает биты версии/варианта UUID, форматирует ID, задаёт version=1 и UTC-время. Пустые map/slice нормализуются, чтобы REST возвращал `{}`/`[]`, а не null. Непосредственное сохранение и проверка ссылок происходят в repository.

`Update` проверяет version и наличие изменений, читает независимую копию товара, применяет только переданные pointers, проверяет итоговый объект и передаёт его с expected version в repository. Конкурирующая запись между Get и Update допустима: финальная CAS-проверка её обнаружит. Время меняется на каждое успешное обновление; клиенты используют version, а не timestamp как механизм блокировки.

## 4. Idempotency cache

Generics `Cache[T any]` позволяют использовать один алгоритм для HTTP response и protobuf.Message. `entry` содержит fingerprint, канал завершения, value/error и срок хранения. Нулевой expires обозначает выполняющуюся функцию.

`Do` сначала проверяет ctx, затем под mutex ищет entry. Завершённая непросроченная запись и выполняющаяся запись используются повторно. Перед ожиданием mutex отпускается; иначе владелец не смог бы завершить запрос. Сравнение `[32]byte` напрямую сравнивает SHA-256. Select ожидающего выбирает отмену или done.

При новой записи Do сначала освобождает просроченные элементы, если достигнут лимит, затем резервирует entry. Функция fn выполняется без mutex. После возврата владелец присваивает value/err, устанавливает TTL или удаляет неудачный запрос, закрывает done и возвращает результат. Отдельный канал передаёт факт готовности, а не копию ответа каждому waiter.

Внутри fn не должно быть panic; весь собственный код возвращает ошибки. Контекст ожидающего не отменяет владельца. Контекст владельца управляет единственным выполнением; после его неудачи новый запрос может стать владельцем новой entry.

## 5. HTTP transport

`Service` описывает контракт, нужный handler. В Routes метод и path входят в pattern стандартного ServeMux Go 1.22. PathValue извлекает ID после маршрутизации. List переводит строковый limit в int, а предметный диапазон проверяет service.

`decode` ограничивает тело, запрещает неизвестные поля и делает второе Decode: нужен EOF, а не второе JSON-значение. Все handlers следуют схеме parse → service → обработка err → JSON. `writeJSON` кодирует до WriteHeader: после отправки заголовков поменять status нельзя. Ошибки сетевой записи логируются. `writeError` сначала различает context, затем domain.Kind; неизвестные ошибки скрываются за 500.

`response` — небольшой буферный ResponseWriter. Первый Write автоматически устанавливает 200, повторный WriteHeader не меняет выбранный status. Replay копирует headers и пишет сохранённые bytes. Буфер не изменяется после публикации в cache.

`Timeout` создаёт child context, запускает обработку с отдельным буфером и ожидает done либо deadline. Канал ёмкости 1 позволяет worker закончить даже после возврата внешнего handler. После дедлайна worker может ещё кратко существовать, но не держит доступ к сетевому writer. Дополнительная ctx.Err после получения результата не позволяет отправить обычный ответ при уже замеченном истечении бюджета.

`Idempotency` пропускает все операции кроме POST /v1/products. Читает ограниченное тело, затем восстанавливает Body для JSON handler. Ошибочный HTTP-результат возвращается вместе с err как значение, поэтому клиент получает исходные status/body, но кеш не сохраняет ошибку. Ошибка самого кеша, где ответа ещё нет, переводится через writeError.

`NewServerHandler` фиксирует порядок: внешний Timeout охватывает чтение ключа/тела, ожидание кеша и service. Middleware создаётся один раз при запуске, поэтому cache не пересоздаётся для каждого запроса.

## 6. gRPC transport

Handler встраивает UnimplementedProductServiceServer для совместимости с generated interface. Преобразование `ToProto` явно связывает domain-поля с контрактом. Timestamp создаётся через timestamppb. Методы handler возвращают domain-ошибки; внешний interceptor выполняет единое преобразование в status, поэтому его подключение в main обязательно.

Optional scalar protobuf-поля представлены pointers. Сообщения Attributes/Images дают отдельный nil-признак для коллекций. ToProto получает уже изолированный domain Product; gRPC-кеш дополнительно клонирует сообщения при сохранении и replay.

Порядок interceptor chain такой же, как у HTTP: Timeout снаружи, Idempotency внутри. Deterministic Marshal стабилизирует fingerprint для protobuf map. Ключ читается из incoming metadata; outgoing metadata используется только в клиенте. Проверки type assertion с `ok` предотвращают небезопасные приведения any.

`toStatus` сохраняет уже готовый gRPC status, отдельно распознаёт context и domain.Kind. Преднамеренные публичные ошибки доступны клиенту, неожиданная внутренняя причина остаётся в логах.

## 7. Client и main

`grpc.NewClient` создаёт переиспользуемое соединение, а реальное подключение происходит лениво при RPC. `insecure.NewCredentials` обозначает plaintext лабораторной. `WithDisableRetry` оставляет единственный контролируемый цикл повторов. Сначала определяется безопасность метода, затем выполняется до трёх вызовов с проверкой кода ошибки и context.

`time.NewTimer` вместо безусловного Sleep даёт возможность прервать backoff через ctx.Done. Сдвиг `5*time.Millisecond << attempt` умножает потолок на степень двойки. Генератор math/rand/v2 для jitter безопасен при параллельном использовании package functions; собственной изменяемой global rand.Source нет.

`main` создаёт logger и signal context, а `run` создаёт dependency graph и оба listener. Канал failures ёмкости 2 не блокирует серверные goroutine, если одновременно завершились оба Serve. Select ожидает сигнал или ошибку; shutdown context создаётся от Background, потому что signal context уже отменён. В shutdown gRPC и HTTP завершаются параллельно, но порядок cleanup остаётся контролируемым.

`cmd/measure` — отдельный инструмент. Он получает реальные HTTP bytes и protobuf response, делает прогрев, планирует open-loop вызовы с 128 workers, собирает latency/error и выводит исходный JSON. Он не входит в путь обслуживания продуктового API.
